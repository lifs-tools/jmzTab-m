This project is the reference reader, writer and validator implementation for mzTab for metabolomics 2.0+, based on the https://github.com/PRIDE-Utilities/jmztab[jmztab project].

mzTab-M is intended as a reporting standard for quantitative results from metabolomics/lipodomics approaches. This format is further intended to provide local LIMS systems as well as MS metabolomics repositories a simple way to share and combine basic information.

mzTab-M has been developed with a view to support the following general tasks:

. Facilitate the sharing of final experimental results, especially with researchers outside the field of metabolomics.
. Export of results to external software, including programs such as Microsoft Excel® and Open Office Spreadsheet and statistical software / coding languages such as R.
. Act as an output format of (web-) services that report MS-based results and thus can produce standardized result pages.
. Be able to link to the external experimental evidence e.g. by referencing back to mzML files.

== Building the project and generating client code from the command-line

In order to build the client code and run the unit tests, execute the following command from a terminal:

	./mvnw install

This generates the necessary domain specific code for a number of different languages, e.g. for Python, JAVA and R.
In general, any language and framework for which swagger-codegen has templates available may be used. For details, please
look at the `api/pom.xml` file and at the https://github.com/swagger-api/swagger-codegen[swagger-codegen repository and documentation].

The generated code is available in the zip archives below the `api/target` directory:

. mztab-api-python https://github.com/lifs-tools/pymzTab-m[GitHub project]
. mztab-api-r https://github.com/lifs-tools/rmzTab-m[GitHub project]

The generated JAVA code is available in a jar archive below the `api/target` directory:

. jmztabm-api-<VERSION>.jar

The generated client libraries only contain the basic domain object code. Parsing from mzTab and writing to mzTab still need to be
implemented separately. The library provides this functionality for JAVA in the `io` sub-project.

== Running a validation with the command-line interface
The `cli` sub-project provides a command line interface for validation of files using the mzTab 2.0 draft validator.

NOTE: Currently, we do not plan to provide a CLI-based validator for mzTab 1.0, since that is still being provided by the original https://github.com/PRIDE-Utilities/jmzTab[jmzTab project].

After building the project as mentioned above with `./mvnw install`, the `cli/target` folder will contain the `cli-<version>-jmztabm-deployment.zip` file. Alternatively, you can download the latest
cli zip file from Maven central: https://central.sonatype.com/artifact/org.lifs-tools/jmztabm-cli[latest cli artefact], under "Browse", or from the https://github.com/lifs-tools/jmzTab-m/releases/latest[latest GitHub release] ("bin.zip").

In order to run the validator, unzip that file, change into the unzipped folder and run

  java -jar jmztabm-cli-<VERSION>.jar

to see the available options.

To validate a particular file with a given level (one of: Info, Warn, Error, where Info includes Warn and Error), run

  java -jar jmztabm-cli-<VERSION>.jar -c examples/MTBLS263.mztab -level Info

To run a semantic validation based on a controlled vocabulary term mapping file, run

  java -jar jmztabm-cli-<VERSION>.jar -c examples/MTBLS263.mztab -level Info -s cv-mapping/mzTab-M-mapping.xml

=== Semantic validation with local controlled vocabularies

The semantic validation looks up the terms of the file in the controlled vocabularies (CVs) it uses, e.g. whether `MS:1000073` is a kind of ion source. By default (`--cvSource local`), the terms are looked up in the vocabulary releases that the file declares in its `cv[1-n]-version` entries. Each release is downloaded once into a local cache and indexed there, so a later run, also without network, checks the file against the same releases and gives the same result.

  java -jar jmztabm-cli-<VERSION>.jar -c examples/MTBLS263.mztab -s

These options change where and how the terms are looked up. They have no short forms.

[cols="1,3"]
|===
|Option |Meaning

|`--cvSource local`
|The default. The terms are looked up in the vocabulary releases in the cache, downloaded when first needed.

|`--cvSource ols`
|The terms are looked up in https://www.ebi.ac.uk/ols4[OLS], as before 2.1. OLS serves only its current release of each vocabulary, not the declared one, so this needs `--cvForce` (see below).

|`--cvCache <folder>`
|The cache folder. The default is `$XDG_CACHE_HOME/jmztabm/cv`, or `~/.cache/jmztabm/cv` if `XDG_CACHE_HOME` is not set or not an absolute path.

|`--cvResources <file>`
|A preferred-resources file, whose entries replace the default's, per vocabulary (see below).

|`--cvOffline`
|No network is used: nothing is downloaded, and OLS is not asked. A release that is not in the cache cannot be had. It cannot be combined with `--cvSource ols`.

|`--cvForce`
|A release that cannot be had is a warning (Warn-3018) instead of an error (Error-3017), and another release is used instead.
|===

==== Which release is used

* Only the vocabularies in which a rule looks up a term are resolved, by the cv label of the parameter. A vocabulary that is declared but not used gets the Warn-3014 as before, and nothing is downloaded for it.
* A declared version that names a release is used as is. A date, e.g. `20-06-2018` or `2018-06-20`, is read as the release that was current on that date. Any other value is treated as undeclared, with Warn-3021.
* A vocabulary without a declared version is checked against its latest release, with Info-3022. "Latest" is always resolved to a concrete release. Which release is the latest, and the list of a vocabulary's releases, are kept in the cache for 24 hours (`<KEY>/latest.json` and `<KEY>/releases.json`); with `--cvOffline` they are used whatever their age. Offline, if the cache holds no latest release kept by an online run, the latest is the newest release in the cache, and the Info-3022 says so.

After the semantic messages, the CLI prints one line per vocabulary used, the release it used, why, and where it came from, for example:

  CV MS: 4.1.2 (SUBSTITUTE_NEWER) from https://raw.githubusercontent.com/HUPO-PSI/psi-ms-CV/v4.1.2/psi-ms.obo
  CV MSIO: 1.0.1 (FILE) from https://raw.githubusercontent.com/MSI-Metabolomics-Standards-Initiative/MSIO/v1.0.1/releases/1.0.1/MSIO-merged-reasoned.owl

The reasons are `FILE` (the declared release), `FILE_DATE` (the release current on the declared date), `FILE_DATE_FALLBACK` (a declared ISO date such as `2021-10-26` that is not a listed release is first looked for as a release of that name; only if it does not exist at its source is it read as a date, and the release current then is used), `MAPPING` (the mapping's version; the bundled mapping names no versions yet, so this comes only once mappings carry versions), `LATEST`, and, in a forced run, `SUBSTITUTE_NEWER`, `SUBSTITUTE_LATEST` and `OLS`. A vocabulary answered by OLS is marked `not re-runnable`: OLS may answer differently once it serves another release.

==== Strict and forced runs

A run is strict by default. A release that cannot be had stops the semantic validation with one Error-3017 for that vocabulary, which names the version and the reason: the release does not exist at its source, the download fails or its checksum does not match a known one, the file cannot be parsed, it is not in the cache while `--cvOffline` is given, or the vocabulary is unknown to the resources file. The remaining rules are skipped, and the run fails, even if the structural validation passed. The structural messages are reported as usual.

With `--cvForce`, the same problems are warnings (Warn-3018), and the validation goes on with the best release it can get: the nearest newer release, then the latest, then OLS's current release. A forced result is therefore not a check against the declared release: each substitute is named in a Warn-3018 and in the report line. With `--cvOffline`, OLS is not asked: a forced offline run substitutes only from the cache, and a vocabulary with no release there is still an Error-3017.

`--cvSource ols` needs `--cvForce`: without it, each vocabulary that is looked up is an Error-3017. With it, each one is a Warn-3018 and marked `not re-runnable`. The version recorded is the one OLS reports (`config.version` of `/api/ontologies/{id}`), else the one its version IRI names, e.g. `4.2.15` for `http://purl.obolibrary.org/obo/ms/4.2.15/ms.owl` (OLS reports PSI-MS this way). A vocabulary for which OLS names neither is an Error-3017 even in a forced run. `--cvSource ols` cannot be combined with `--cvOffline`.

The exit code follows the same rule as before: the run fails if a message at or above the chosen level (`-l`) is a warning or an error. The new warnings (3018 to 3021 and 3023) therefore fail a run at the levels Info (the default) and Warn; run with `-l Error` to fail on errors only.

==== The cache

* The cache holds one folder per vocabulary and release, `<cache>/<KEY>/<version>/`, with the downloaded file, its index `terms-v<n>.idx` (`n` is the index version of the jmzTab-m build, currently 3) and a `release.json` that records where the file came from, its SHA-256 checksum and when it was downloaded. `KEY` is the key of the vocabulary in the resources file, e.g. `MS` or `NCBITaxon`.
* A release is never downloaded again. Files are written under a temporary name and then renamed, so several runs can share one cache folder.
* When an upgrade of jmzTab-m changes how vocabulary files are read, the first run that needs a cached release builds the new version's index from the cached file, without downloading it again and also with `--cvOffline`. It first checks the cached file and its cached imports against the SHA-256 in `release.json`; a file that differs or is missing is a corrupt entry, `CHECKSUM_MISMATCH` (an Error-3017 in a strict run), and the folder is left as it is: delete it to download the release again. The index of another version, such as an older build's `terms.idx`, is left in place and not read, so builds of different versions can share one cache.
* The first run that needs a release downloads it, and logs its size, e.g. `Downloading MS 4.1.2 (699.3 kB) from https://...`. Some vocabularies are large: the releases of NCBITaxon, NCIT and CHEBI are hundreds of MB each. There is no size limit.
* An OWL vocabulary's imports are downloaded and cached with it, under `<cache>/_imports/`. An import whose IRI names no version is kept as it was first downloaded; delete its folder to download it again.
* Every download of the default resources file starts over https, and a redirect from https to plain http is refused, as a cached release is kept and checksummed for good. An import IRI on `http://purl.obolibrary.org` is fetched over https; `release.json` records the IRI as written and the URL it came from. CHEBI is fetched from the EBI FTP archive, which this way serves releases 245 and later; for an older release, give its `chebi_legacy` location in a `--cvResources` entry.
* The GitHub API, which lists the releases of e.g. PSI-MS and MSIO, allows 60 requests per hour without a token. Set the environment variable `GITHUB_TOKEN` to a GitHub token to use your own limit.
* To validate without network, pre-fill the cache: copy a cache folder from a machine that has the releases, or put the vocabulary file alone into `<cache>/<KEY>/<version>/`, under the name of its download (the last part of its URL, e.g. `MS/4.1.2/psi-ms.obo`). The first run that needs it builds its index and writes its `release.json`, also with `--cvOffline`.
** A pre-filled release answers a file that declares that release. A file without a version, or with a value that names no release, is checked against the latest release: offline, that is the one an earlier online run kept, else the newest release in the cache.
** A declared date, e.g. `20-06-2018`, needs the list of the vocabulary's releases with their dates. Offline, only a list that an earlier online run kept (`<KEY>/releases.json`, so copy a whole cache folder), or one written out in a `--cvResources` entry (`"releases": {"kind": "listed", ...}`, see below), gives it. Without one, a date is an Error-3017 offline; with `--cvForce`, the newest release in the cache is used instead, with a Warn-3018.

==== The resources file

Where the releases of a vocabulary come from is set in a preferred-resources file. jmzTab-m ships a default, https://github.com/lifs-tools/jmzTab-m/blob/master/validation/src/main/resources/cv/preferred-resources.json[cv/preferred-resources.json], for the vocabularies of the bundled mapping file: PSI-MS, DOID, CL, BTO, NCBITaxon, UO, NCIT, PRIDE, MSIO, CHEBI and OBI. Its schema is https://github.com/lifs-tools/jmzTab-m/blob/master/validation/src/main/resources/cv/preferred-resources.schema.json[cv/preferred-resources.schema.json]. Each entry gives:

* `labels`: the `cv[1-n]-label` values the vocabulary is known by, and `oboPrefix`, the prefix of its term ids;
* `location`: the `format` (`OBO`, `OBO_GZ` or `OWL_RDFXML`) and either a `urlTemplate` with `{version}` or an `oboFoundryId`;
* `scheme`: how its versions are compared, `DOTTED` (`4.1.30`), `ISO_DATE` (`2023-05-25`) or `RELEASE_NUMBER` (`230`);
* `releases`: how its releases and their dates are listed: `githubTags`, `directoryListing`, or `listed` (written out);
* `latest`: how its latest release is found: `githubLatestTag`, `header` or `newestRelease`;
* optionally `knownSha256`, known checksums of release files by version.

A file given with `--cvResources` replaces the default's entries with the same key; the other default entries stay. The file is checked against the schema when it is read. An invalid file stops the run before the validation, with a message that names the entry and the JSON pointer of the problem. For example, to get PSI-MS from a mirror, with the one release it holds:

[source,json]
----
{
  "vocabularies": {
    "MS": {
      "labels": ["MS", "PSI-MS"],
      "oboPrefix": "MS",
      "location": {"format": "OBO", "urlTemplate": "https://mirror.example.org/psi-ms/{version}/psi-ms.obo"},
      "scheme": "DOTTED",
      "releases": {"kind": "listed", "releases": [{"version": "4.1.200", "date": "2025-01-15"}]},
      "latest": {"kind": "newestRelease"}
    }
  }
}
----

  java -jar jmztabm-cli-<VERSION>.jar -c examples/MTBLS263.mztab -s --cvResources my-resources.json

==== Messages

[cols="1,3"]
|===
|Code |Meaning

|Error-3017
|A vocabulary release is not available, in a strict run. The semantic validation stops.

|Warn-3018
|A vocabulary release is not available, in a forced run; another release, or OLS, was used instead.

|Warn-3019
|The file declares an older release than the one the mapping rules were written for. Only with a mapping that names vocabulary versions; the bundled mapping does not yet.

|Warn-3020
|The declared release cannot be compared with the mapping's version; the declared one is used. Only with a mapping that names vocabulary versions, as Warn-3019.

|Warn-3021
|The declared version is not a version value; it is treated as undeclared.

|Info-3022
|No version is declared; the latest release was used.

|Warn-3023
|The same cv label is declared twice; the first entry is used.
|===

=== Converting to JSON

If you want to exchange your mzTab-M model in JSON format, you can transcode your mzTab-M TSV file into JSON as follows:

  java -jar jmztabm-cli-<VERSION>.jar -c examples/gcxgc-ms-example.mztab -toJson -s cv-mapping/mzTab-M-mapping.xml

This will create a new file on successful validation, named <inFile>.json (inFile without any paths) that contains your mzTab-M data serialized as JSON.

NOTE: Comments are retained within the comments part of the JSON document but not at their original locations.

=== Converting from JSON

If you only have a JSON model of your mzTab-M file available, you can convert it using the command line as follows:

  java -jar jmztabm-cli-<VERSION>.jar -c examples/gcxgc-ms-example.mztab.json -fromJson -s cv-mapping/mzTab-M-mapping.xml

This will create a new file on successful validation, named <inFile>.mztab (inFile without any paths) that contains your mzTab-M data serialized in TSV format.

NOTE: Comment objects are currently discarded by the mzTab-M TSV serializer.

If you have not done so, please build the Docker image of the validator cli or pull it from the docker hub (see previous sections).
Then, run the following command, replacing `<VERSION>` with the current version, e.g. `1.0.6`) and `<DATA_DIR>` with the **local** directory containing your mzTab-M files:

  docker run -v <YOUR_DATA_DIR>:/home/data:rw lifs/jmztabm-cli:<VERSION>

This will only invoke the default entrypoint of the container, which is a shell script wrapper calling the jmztab-m-cli Jar. It passes all arguments to the validator, so that all

== Migrating from 1.0.x to 2.1

jmzTab-m 2.1 replaces the string-based logical column positions inherited from jmzTab 1.0, which limited the number of columns per table section (see https://github.com/lifs-tools/jmzTab-m/issues/187[#187]). Command-line users are not affected. If you use the column model (`uk.ac.ebi.pride.jmztab2.model`) directly:

* `IMZTabColumn.getLogicPosition()` is now `getPosition()` and returns a `ColumnPosition(order, index, elementId)` record, compared numerically. `setLogicPosition(String)` was removed; the position is derived from order, index and element.
* `getOrder()` / `setOrder(...)` use `int` instead of `String`. Stable column orders are `1..n`.
* `MZTabColumnFactory` maps are keyed by `ColumnPosition` and are unmodifiable. Register columns via `addStableColumn(column, order)`, `addOptionalColumn(..., order)`, `addAbundanceOptionalColumn(..., order)` or `addIdConfidenceMeasureColumn(..., order)`; the variants without `order` append at `nextOrder()`. All `add...` methods return the assigned `ColumnPosition` and throw `IllegalArgumentException` if the position or header is already taken. `MZTabColumnFactory` also gained `nextOrder()` and `getAbundanceColumnMapping()`.
* `AbundanceColumn.createOptionalColumns(Section, StudyVariable, String, String)` is now `createOptionalColumn(Section, StudyVariable, String, int)` and returns a single column. `OptionColumn` and `ParameterOptionColumn` constructors take the column's own order instead of the previous column's offset.
* `AbundanceColumn.createOptionalColumn(Section, Assay, int)` keeps its signature, but the `int` argument is now the column's own order (previously an offset; the column was placed at `offset + 1`).
* `AbundanceColumn.createOptionalColumns(Section, StudyVariable, int lastOrder)` still exists; it now places the study-variable and variation columns at `lastOrder + 1` and `lastOrder + 2` (previously `+2`/`+3`) and returns `SortedMap<ColumnPosition, MZTabColumn>`.
* `id_confidence_measure[n]` columns created by `MZTabColumnFactory.addIdConfidenceMeasureColumn` now report `isOptional() == true` (previously `false`); they were already kept in the optional column mapping.
* `PositionMapping` maps physical positions directly to `IMZTabColumn`; `reverse()` was removed.
* Duplicate column headers in a table section are reported as the new logical error `DuplicateColumnHeader` (code 2062).

== Using the API programmatically

=== Reading mzTab 2.0 with structural and logical validation

NOTE: As of version 1.0.8, the package structure has been adapted to the new `groupId`. In your imports, please replace `de.isas.mztab2` and `de.isas.lipidomics.mztab2` with `org.lifstools.mztab2`

The following snippet will parse an mzTabFile from a file on disk:

  import uk.ac.ebi.pride.jmztab2.*;
  import uk.ac.ebi.pride.jmztab2.utils.*;
  import uk.ac.ebi.pride.jmztab2.utils.errors.*;
  import org.lifstools.mztab2.io.*;
  import org.lifstools.mztab2.model.*;
  ...
  File mzTabFile = new File("/path/to/my/file.mztab");
  MzTabFileParser parser = new MzTabFileParser(mzTabFile);
  //will report a maxmimum of 500 errors on Error, Warn and Info levels
  //will output errors to System.err (onto your terminal)
  parser.parse(System.err, MZTabErrorType.Level.Info, 500);
  //inspect the output of the parse and errors
  MZTabErrorList errors = parser.getErrorList();
  //converting the MZTabErrorList into a list of ValidationMessage
  List<ValidationMessage> messages = errors.convertToValidationMessages();
  //access the file after parsing
  MzTab mzTab = parser.getMZTabFile();

=== Creating an mzTab 2.0 object model

The mzTab domain model uses a _builder_ pattern, but also conforms to the usual JAVA _bean style_ pattern. The _builder_ pattern allows for a more fluent definition of your object structure. However, especially for cross references with the file, you will need to define e.g. MsRun objects separately since inline referencing within the builder code will not work.

The following code will create the first parts of an mzTab-M file programmatically:

  import org.lifstools.mztab2.model.*;
  ...
  MzTab mztab = new MzTab();
  Metadata mtd = new Metadata();
  mtd.mzTabVersion("2.0.0-M");
  mtd.mzTabID("1");
  mtd.addSoftwareItem(new Software().id(1).
      parameter(new Parameter().id(1).
          name("LipidDataAnalyzer").
          value("2.6.3_nightly")));
  MsRun msrun1 = new MsRun().id(1).
      location(
          "file://D:/Experiment1/Orbitrap_CID/negative/50/014_Ex1_Orbitrap_CID_neg_50.chrom");
  mtd.addMsRunItem(msrun1);
  Assay a1 = new Assay().id(1).
      addMsRunRefItem(msrun1);
  Assay a2 = new Assay().id(2).
      addMsRunRefItem(msrun2);
  mtd.addAssayItem(a1).addAssayItem(a2);
  ...

=== Writing mzTab 2.0 with validation

The following code writes an mzTab object structure to the provided file path,
performing structural and logical validation:

  MzTabValidatingWriter writer = new MzTabValidatingWriter();
  File f = File.createTempFile(UUID.randomUUID().toString(), ".mztab");
  Optional<List<ValidationMessage>> messages = writer.write(f.toPath(), mzTab);

You can also pass an `OutputStreamWriter` to the `write` method.

=== Writing mzTab 2.0 without validation

The following code writes an mzTab object structure to the provided output stream _without_ any validation (use at your own risk):

  MzTabNonValidatingWriter writer = new MzTabNonValidatingWriter();
  try (ByteArrayOutputStream baos = new ByteArrayOutputStream()) {
      try (OutputStreamWriter osw = new OutputStreamWriter(
          baos, Charset.forName("UTF8"))) {
          writer.write(osw, mzTab);
          osw.flush();
	  String mzTabFileAsAString = osw.toString();
      }
  }

Alternatively, you can also provide a File path to the `write` method.

== Editing the Swagger Spec
This project defines the structure of an mzTab document based on JSON-Schema
and Swagger https://swagger.io/.

Swagger provides many templates to generate client / server implementations
based on a Swagger yaml or json definition.

This mechanism can be used to generate the domain-specific model classes in
any of the supported languages, omitting the web-specific parts.

The https://editor.swagger.io/[Swagger editor] can be used to import the file,
edit it with assistance and preview, and export it after editing. It additionally
supports the generation of server and client code to represent the mzTab object structure.

To launch the editor via https://www.docker.com/[Docker] on Unix, use the script
`run-swagger-editor.sh` in this directory.

The swagger API definition is in the following file: `api/src/main/resources/mzTab_m_swagger.yml`.

You can open it in the Swagger Editor via File -> Import File. If you are done editing, go to File -> Download YAML and save the file at the location of the mzTab_m_swagger.yml file, thereby replacing the original file.

You can create server and client code in a multitude of languages from the Generate Server and Generate Client menu items.
