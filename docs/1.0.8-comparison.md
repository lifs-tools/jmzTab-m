# 1.0.7-SNAPSHOT to 1.0.8-SNAPSHOT behaviour comparison

## What was compared

- Baseline: commit `53242461` (1.0.7-SNAPSHOT, the build the validator uses today).
- New line: `release/1.0.8` at `1a0c44ab` (1.0.8-SNAPSHOT), the measured commit. The
  commit that adds this text changes only this file. Range `53242461..1a0c44ab`:
  - `4c3e8079` report all missing abundance columns in SMH/SFH headers, assays first
    (from master `910bc44b`),
  - `3cef606f` CLI fails on unreadable JSON (from master `b7c36c3f`; CLI only, does not
    touch `MzTabFileParser`),
  - `cf49da16` version bump to 1.0.8-SNAPSHOT,
  - the backport of linked, fix-first validation messages: the seven master commits
    `48b8e496^..2711c0bf` (optional `suggestion`, `rule_id` and `location` on
    `ValidationMessage`) and the five master follow-ups `1b979204^..428f8893` (at most
    100 located semantic messages per rule and term, two fix texts, field descriptions,
    `study_variable_group[n]` locations),
  - documentation only: `08687dfa` and `c312d25d` (this file), `1a0c44ab` (release notes).
- Method: both builds (`./mvnw -B -q package -DskipTests -DskipITs`, no `install`) run
  `new MzTabFileParser(file).parse(new ByteArrayOutputStream(), MZTabErrorType.Level.Info, 10000)`
  over every file; each build uses only its own jmztabm jars (cli jar plus `cli/target/lib`).
  `parse` closes the stream it is given when validation stops early and then prints the
  error list to it; a `ByteArrayOutputStream` stays writable after `close()`, so the messages
  of such files are compared too.
  One line per message (file id, level, code, line, whitespace-normalised message text),
  sorted so message order does not count, then `diff`ed. A message text change on an
  otherwise equal line would therefore also show up. The new `suggestion`, `rule_id` and
  `location` fields are not part of the compared output.

## Inputs

| Set | Files | Messages (1.0.7 / 1.0.8) | Exceptions (1.0.7 / 1.0.8) |
|---|---|---|---|
| Fixtures: `test-utils/src/main/resources/**/*.mztab` (case-insensitive) | 32 | 75 / 75 | 0 / 0 |
| Private corpus (lipidcompass submissions and studies) | 1,483 | 4,285 / 4,285 | 0 / 0 |

Fixture messages by level and code, both builds: Error-2008 x1, Error-2050 x23,
Error-2053 x2, Error-2054 x1, Warn-2056 x1, Info-2052 x14, Info-2057 x33.
Corpus messages by level and code, both builds (counts only): Info-2057 x2,788,
Info-2052 x1,466, Error-1008 x5, Error-1009 x5, Error-1012 x7, Error-1013 x7,
Error-2000 x7.

The 31 error messages come from 17 corpus files where validation stops early. An earlier
version of this comparison passed `OutputStream.nullOutputStream()`, which throws once
`parse` has closed it, so these files showed up as 17 `java.io.IOException` on both builds
and their messages were not compared. They are now, and are identical on both builds.

## Result

- Fixtures: the sorted outputs are byte-identical. No per-code count differs, 0 files affected.
- Corpus: the sorted outputs are byte-identical. No per-code count differs, 0 files affected.
- Every difference is therefore explained (there are none): no regression, and no change
  caused by anything other than the two ported fixes.

The corpus and the fixtures contain no file whose header lacks abundance columns, so the
fix is not exercised by them. To show that the comparison can see the fix, three derived
files (a public fixture, `metabolomics/official-profile-ms.mztab`, with abundance columns
removed from SMH and SML) were run through both builds:

| Derived file | 1.0.7-SNAPSHOT | 1.0.8-SNAPSHOT |
|---|---|---|
| all `abundance_*` columns removed (365) | 1 x Error-2009 (`NotDefineInHeader`) for `abundance_study_variable[1]`, then validation stops | 365 x Error-2009 on the SMH line, one per missing column, including the one 1.0.7 reports |
| `abundance_assay[2]` and `[3]` removed | 1 x Error-2009 for `abundance_assay[2]`, then validation stops | 2 x Error-2009, for `abundance_assay[2]` and `[3]` |
| `abundance_assay[2]`, `abundance_study_variable[1]` and `abundance_variation_study_variable[1]` removed | 1 x Error-2009 for `abundance_study_variable[1]` (study variables were checked first), then validation stops | 3 x Error-2009, assay column first |

All differences are extra Error-2009 on the SMH line: the intended effect of `4c3e8079`,
which reports all missing abundance columns, assays first, instead of stopping at the first
one. The derived files are not committed; the comparison scripts are kept outside the
repository.

## Rerun after the backport of linked, fix-first validation messages

The first run measured `cf49da16`. After the seven master commits `48b8e496^..2711c0bf`
were cherry-picked onto `release/1.0.8`, the comparison was rerun and showed no change.
The run above repeats it at `1a0c44ab`, after the five follow-ups, with the corrected
output stream (which is why the corpus now shows 31 messages where it showed 17
exceptions) and with corrected derived files for the positive control (the two partial
removals had not removed any column before). The backport adds fields to messages, not
messages.

The comparison covers `MzTabFileParser` only. The backport also changes the semantic
(CV mapping) validation, which this comparison does not run: messages about terms that
are not allowed are now reported once per affected element, at most 100 per rule and term
with a location, plus one message without location for any further elements, so their
count can rise.
