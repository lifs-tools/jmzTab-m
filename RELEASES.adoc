== Publishing a snapshot

The CI workflow publishes snapshots on every push to `master` and `1.0.x`: to GitHub Packages (`-Pgithub-snapshot`) and to the LIFS Tools Artifactory (`-Pjfrog`, https://m.lifs-tools.org/artifactory/lifs-libs-snapshot-local/). Snapshots are not published to Maven Central.

== Publishing a release

A release is staged and published from your machine with `scripts/release.sh`, so that the signing key never leaves it:

* `scripts/release.sh stage` builds all modules from scratch with `./mvnw -B -Pcentral-release -DskipUpload=true clean deploy`, which runs the unit and integration tests and signs every file. It checks that the bundle holds the six modules `jmztabm` (parent POM), `jmztabm-api`, `jmztabm-io`, `jmztabm-validation`, `jmztabm-cli` and `jmztabm-test-utils`, each with its POM, jar, sources and javadoc jars and their `.asc` signatures. It uploads the bundle to the Central Portal and waits for the validation, but does not publish it. It refuses to run with uncommitted changes, with a SNAPSHOT version, or when the checked out commit is not tagged `release-<version>`.
* `scripts/release.sh publish <id>` publishes exactly the staged files, without building again, after you type the deployment name to confirm. It then waits until the Portal reports them as published. `scripts/release.sh drop <id>` drops the deployment instead.

Both refuse a deployment that is not named "jmzTab-m …" or contains components other than `org.lifs-tools:jmztabm*`. They use `scripts/central-portal.sh`, a small client of the https://central.sonatype.org/publish/publish-portal-api/[Publisher API], and need `curl` and `jq`.

=== Credentials (once)

. A user token of the Central Portal (https://central.sonatype.com/account, "Generate User Token") for an account that may publish to the namespace `org.lifs-tools`. `scripts/release.sh` asks for it, or reads it from the environment variables `CENTRAL_TOKEN_USERNAME` and `CENTRAL_TOKEN_PASSWORD`.
. A GPG key whose public key is on a key server, e.g. `gpg --keyserver keyserver.ubuntu.com --send-keys <KEY_ID>`. The default key is used; pass `-Dgpg.keyname=<KEY_ID>` for another one (`scripts/release.sh stage -Dgpg.keyname=<KEY_ID>`). The passphrase comes from the gpg agent or from the environment variable `MAVEN_GPG_PASSPHRASE`.

=== Steps

The example releases 2.1.0 from `master`. A 1.0.x release is made the same way from the `1.0.x` branch.

. Check that the CI build of the branch passed. The CI build runs `package` only, without the integration tests; `scripts/release.sh stage` runs them.
. In the release notes below, replace "(unreleased)" with the release date.
. Set the release version, commit and tag:
+
----
./mvnw versions:set -DnewVersion=2.1.0 -DgenerateBackupPoms=false
git commit -am "Release 2.1.0"
git tag release-2.1.0
----
. Build, test, sign and upload all modules to the Central Portal:
+
----
scripts/release.sh stage
----
+
At the end it prints the deployment id and the commands to publish or drop it. If the build or the validation fails, fix the problem, move the tag (`git tag -f release-2.1.0`) and stage again.
. Check the deployment "jmzTab-m 2.1.0" at https://central.sonatype.com/publishing/deployments. To try the staged artifacts in another project first, see "Testing a staged deployment" below. Then publish it:
+
----
scripts/release.sh publish <DEPLOYMENT_ID>
----
+
If something is wrong, `scripts/release.sh drop <DEPLOYMENT_ID>`, fix it and stage again: a published version cannot be changed or deleted. "Publish" and "Drop" in the portal do the same.
. Push the release commit and the tag:
+
----
git push origin master release-2.1.0
----
. Create the GitHub release `release-2.1.0` at https://github.com/lifs-tools/jmzTab-m/releases with the release notes of the version and these files:
* the CLI distribution, `cli/target/jmztabm-cli-2.1.0-bin.zip`;
* the native validators from the workflow run of the release commit (Actions, the run, "Artifacts"), under the names of the `dev-latest` pre-release: `jmztabm-validator-amd64-linux`, `jmztabm-validator-aarch64-macos` and `jmztabm-validator-amd64-windows.exe`.
+
For example, with the GitHub CLI:
+
----
gh run download <RUN_ID> -R lifs-tools/jmzTab-m -D dist
mkdir release
cp cli/target/jmztabm-cli-2.1.0-bin.zip release/
cp dist/jmztabm-validator-amd64-linux/jmztabm-validator release/jmztabm-validator-amd64-linux
cp dist/jmztabm-validator-aarch64-macos/jmztabm-validator release/jmztabm-validator-aarch64-macos
cp dist/jmztabm-validator-amd64-windows/jmztabm-validator.exe release/jmztabm-validator-amd64-windows.exe
gh release create release-2.1.0 -R lifs-tools/jmzTab-m --verify-tag --title "jmzTab-m 2.1.0" --notes-file notes.md release/*
----
. Set the next development version, e.g. `./mvnw versions:set -DnewVersion=2.1.1-SNAPSHOT -DgenerateBackupPoms=false`, add a new "(unreleased)" section to the release notes, commit and push.

Without the script, `./mvnw -B -Pcentral-release deploy` stages a release too: the plugin uploads the bundle itself, with the token from server `central` in `~/.m2/settings.xml` (`<username>` and `<password>`), and you publish it in the portal. It does not check the bundle or the tag.

=== Testing a staged deployment

A validated deployment can be used as a Maven repository before it is published (https://central.sonatype.org/publish/publish-portal-api/[Publisher API], "Manually testing a deployment bundle"). The Portal expects the header `Authorization: Bearer <token>`, where `<token>` is the output of `printf '%s:%s' '<token username>' '<token password>' | base64`. Add it to `~/.m2/settings.xml`:

----
<servers>
  <server>
    <id>central.manual.testing</id>
    <configuration>
      <httpHeaders>
        <property>
          <name>Authorization</name>
          <value>Bearer <!-- token --></value>
        </property>
      </httpHeaders>
    </configuration>
  </server>
</servers>
<profiles>
  <profile>
    <id>central.manual.testing</id>
    <repositories>
      <repository>
        <id>central.manual.testing</id>
        <url>https://central.sonatype.com/api/v1/publisher/deployments/download/</url>
      </repository>
    </repositories>
  </profile>
</profiles>
----

Then build a project that uses jmzTab-m 2.1.0 with `-Pcentral.manual.testing`.

== Release notes

=== 2.1.0 (unreleased)

. *Migration from 1.0.6:* the Maven `groupId` is `org.lifs-tools`; up to 1.0.6 it was `de.isas.mztab` (1.0.7 was not released, 1.0.8 is the first 1.0.x release with the new `groupId`). The `artifactId`s are unchanged. The Java packages `de.isas.mztab2.*` are now `org.lifstools.mztab2.*`, and `de.isas.lipidomics.mztab2.validation.*` (bean validation in `jmztabm-api`) is now `org.lifstools.mztab2.validation.*`; `uk.ac.ebi.pride.jmztab2.*` is unchanged. Releases are published through the Central Portal (see "Publishing a release"); OSSRH was shut down.
. Validation messages may carry `suggestion`, `rule_id` and `location` (optional, additive). Semantic messages about terms that are not allowed are now reported once per affected element, so their count can rise: at most 100 messages per rule and term name their element, further elements with the same term are reported together in one message without location that gives their number.
. A parameter with an undefined cv label (Error-3013) is reported once, where it is defined. Before, `CvMappingValidator` ran the check twice, and the check reported the parameter again for every reference that reaches it (ms_run, assay, study variable, evidence spectra_ref), e.g. 16 messages for one instrument name.
. The parser builds the model unless there is an error; warnings and infos on data lines no longer drop it. Before, a file with such a warning (e.g. an unsupported `ms_run[1-n]-id_format`) got a model at level Error but none at level Info or Warn, so the reference, colunit and profile checks that need the model did not run and can now report further messages.
. `MZTabErrorList.addAll` applies the level filter and the maximum number of messages like `add`; before, messages added through it were reported at every level. New `MZTabErrorList.hasErrors()`.
. *Behaviour change:* every instrument must be referenced by an `ms_run[1-n]-instrument_ref` (new Error-2065) and every sample by an `assay[1-n]-sample_ref` (new Error-2066) (#89, #33). A single study variable without `assay_refs` is now an error (Error-2012), and the single study variable "undefined" must reference all assays (new Error-2064) (#91). These reference checks run after the model is built, so the file is still read. Most files from LipidCompass define one instrument and no `instrument_ref` and now fail with Error-2065.
. A file whose only study variable is not `study_variable[1]` no longer crashes the parser (NullPointerException).
. `study_variable[1-n]-factors` (mzTab-M 2.0) is validated; a file that declares mzTab-M 2.1 or later gets Warn-2067, since 2.1 replaced it by `study_variable_group[1-n]` (#186). This version does not keep factors; jmzTab-m 1.0.x reads and writes them. A `study_variable[n]` name line no longer discards properties read before it.
. *Behaviour change:* a term that a CV mapping rule does not allow (3005, 3009) takes the rule's requirement level: MUST error, SHOULD warning, MAY info (#186). Before, it was always a warning.
. Semantic validation no longer aborts on a parameter whose accession is not `<CV label>:<term number>` or that has an accession but no cv label: it is reported as the new Error-3016 at the parameter (#185). A rule, pre or post validator that fails is reported as Error-3015 for that rule only; the others still run. A cv label defined twice no longer aborts it.
. CLI: semantic validation (`-s`) also runs when the structural validation reported warnings or errors; a missing or invalid mapping file, a file without a model and an exception during semantic validation are reported instead of ending silently; with `-o`, nothing is lost when the output file is closed; any exception fails the run.
. The validation jar no longer contains `logback-test.xml`, which made the CLI, the native binary and applications using the library log at DEBUG with a status dump; the CLI's `logback.xml` uses `${LOG_LEVEL:-INFO}` (#193). The native validator's metadata now also registers logback's `LevelChangePropagator`, which that `logback.xml` declares; before, it was missing from the native image.
. *Behaviour change:* a list of references (`assay_refs`, `study_variable_refs`) must be separated by `|`. Before, `assay[1], assay[2]` was silently read as `assay[1]`; now any other separator, an empty entry (`assay[1]|`) or extra text is Error-1002. A single reference (`instrument_ref`, `sample_ref`, `ms_run_ref`) must be exactly one element.
. A reference above the lines of its element, e.g. an `ms_run[1]-instrument_ref` before `instrument[1]` is defined, is the new Error-2068 and is still resolved. Before, it ended parsing with Error-2008. A reference to an element that is never defined is still Error-2008, but no longer ends parsing.
. Mapping rules (`mzTab-M-mapping.xml`): the quantification unit rules also accept NCIT units of concentration (`NCIT:C48207`) and amount of substance (`NCIT:C48453`), and quantification datatypes (`MS:1001805`); the confidence measure rules also accept spectral similarity scores (`MS:1003303`). Rules on a column of the summary, feature or evidence table don't apply to a file without that table, and neither do the rules on `id_confidence_measure` (needed with an evidence table) and the summary and feature quantification units, as in the profile checks.
. `CvMappingValidator.of(File, boolean)` looked up every term at `https://https://…` and reported each as Error-3015. All factories and `new CvParameterLookupService()` now use OLS4 (`CvParameterLookupService.defaultConfig()`).
. The writer no longer writes the header of a table without rows when the file's `mzTab-profile` has no such table. Before, a profile "M" file (e.g. converted from JSON with `--fromJson`) was written with empty SMH, SFH and SEH sections and then failed validation with Error-2039. Files without a profile (mzTab-M 2.0) are written as before.
. Bundled examples: `minimal-m-2.0.mztab` uses `|` in `assay_refs` and the instrument accession `MS:1000449`; `example_study_variable_group.mztab` names HMDB with a user parameter instead of a MIRIAM accession.
. A metadata parameter with more than four fields, e.g. a name with unquoted commas (`[MS, MS:1002584, qtof 9000 (example vendor, city, country), ]`), is reported as Error-1012 at its line, and the validation goes on. The `instrument[n]`, `software[n]` or `ms_run[n]` is still defined, without that property, so references to it resolve. Before, on the first line of an `instrument[n]`, `software[n]` or `ms_run[n]` it also ended the validation with Error-2000 ("Column "instrument[1]" is an empty cell"), and the lines after it were not checked. The messages of Error-1012 and Error-1013 now say that a parameter has the four fields [CV label, accession, name, value] and that a name or value with commas must be in double quotes (`[, , "a, b", ]`).
. Values that ended the validation with an exception, or were reported as a generic Error-2000, are reported at the value (#251, #249): a `cv[1-n]-uri` or an SML `uri` that is not a URI (e.g. it contains a space) is Error-1015; before, an IllegalArgumentException ended the run. An `opt_` column like `opt_global_cv_MS:1002217`, which has no accession, is Error-1007 at the column. An empty publication item (`pubmed:1||doi:…`) is Error-1014.
. *Behaviour change:* a publication item is split at its first `:`, so a DOI that contains `:` is valid, and only the type is case-insensitive: the accession keeps its spelling (before, it was lowercased) (#249). Only a DOI itself (`10.…`) may contain `:`: a DOI URL (`doi:https://doi.org/10.…`), a doubled `doi:doi:` or a PubMed id with `:` is still Error-1014, as in 1.0.6, so a wrong separator after either is still found.
. The messages of the list errors (Error-1021, 1022, 1033) name the split character as the third value, `{2}`, so tools that fill the templates by index, as the fix texts are filled, show the split character instead of the value; the message and cause of Error-1021 no longer start with `=` (#243).
. All missing mandatory columns of an SMH, SFH or SEH header are reported, one Error-1004 each (#244). Before, validation stopped at the first.
. `MzTabFileParser.parse` no longer closes the stream it writes to after an error that ends the validation, or after too many messages. The CLI and the native validator pass the console there, so they printed nothing after the stack trace: neither the messages found before, e.g. the other missing columns (#244), nor the summary.
. JSON (#194, #218): metadata elements with an id (`ms_run`, `assay`, `sample`, `study_variable`, `instrument`, `cv`, `database`, …; the 13 schemas marked `x-mztab-serialize-by-id`) are read from and written as their id when they are referenced, as in 1.0.6. Before, JSON written by 1.0.6 (e.g. `"sample_ref": 1`) could not be read, and `--toJson` wrote nested copies instead of ids. The annotation is declared in the OpenAPI spec (`x-class-extra-annotation`), so a regenerated model keeps it. With `--fromJson`, a file that contains only `null` fails with a message and no mzTab file is written; before, an empty one was written and a NullPointerException was reported. Still not readable: JSON whose `scan_polarity` is a string instead of a list of parameters, as in the MetaboScape example of HUPO-PSI/mzTab-M.
. *Behaviour change:* semantic validation checks terms against the vocabulary releases a file declares (`cv[1-n]-version`), from a local cache, instead of OLS's current release (design: reproducible semantic validation, phase 1). Each release is downloaded once into the cache (`$XDG_CACHE_HOME/jmztabm/cv`, else `~/.cache/jmztabm/cv`), indexed, and never downloaded again; the first run downloads what it needs and logs its size, which is hundreds of MB for NCBITaxon, NCIT and CHEBI. Where the releases come from is set in a preferred-resources file with a JSON Schema (`cv/preferred-resources.json` and `cv/preferred-resources.schema.json` in `jmztabm-validation`); jmzTab-m ships a default for the vocabularies of the bundled mapping. Every download of the default file starts over https, and a redirect from https to http is refused; an OWL import on `http://purl.obolibrary.org` is fetched over https and recorded under its IRI as written. CHEBI comes from the EBI FTP archive over https (its PURL redirects to plain http), which serves releases 245 and later. The "latest" release and the release lists are cached for 24 hours, and used at any age with `--cvOffline`; offline, without them, the latest release is the newest one in the cache. An OWL import whose IRI names no version is kept as first downloaded. See the README, "Semantic validation with local controlled vocabularies".
. CLI: new options for semantic validation, all without short forms: `--cvSource local|ols` (default `local`), `--cvCache <folder>`, `--cvResources <file>` (entries replace the default's per vocabulary; an invalid file stops the run before the validation, naming the entry and the JSON pointer), `--cvOffline` (no network: no downloads and no OLS, so a forced offline run substitutes only from the cache; the cache can be pre-filled; not with `--cvSource ols`, which is rejected before the validation) and `--cvForce`. After the semantic messages, the CLI prints one line per vocabulary used: `CV <label>: <version used> (<reason>) from <source>`, with `, not re-runnable` for an answer from OLS.
. New semantic messages: Error-3017 (a vocabulary release is not available; in a strict run the remaining rules are skipped and the validation fails), Warn-3018 (with `--cvForce`: another release, or OLS, was used instead), Warn-3019 (the declared release is older than the mapping's) and Warn-3020 (the two versions cannot be compared), which need a mapping that names vocabulary versions (the bundled one does not yet), Warn-3021 (the declared version is not a version value), Info-3022 (no version declared; the latest was used) and Warn-3023 (a cv label declared twice).
. *Behaviour change:* the new warnings 3018 to 3021 and 3023 fail a run at the levels Info (the default) and Warn, as the CLI's exit rule is the same as before: a run fails if a message at or above the chosen level is a warning or an error. Run with `-l Error` to fail on errors only; with `--cvForce`, a release that cannot be had is a warning instead of an error.
. *Behaviour change:* `--cvSource ols` checks against OLS's current release, which is not the declared one, so it now needs `--cvForce`: without it, each vocabulary that is looked up is an Error-3017. With it, each is a Warn-3018 and marked not re-runnable. The version recorded is OLS's `config.version`, else the version its version IRI names (OLS4 reports PSI-MS only as `.../obo/ms/4.2.15/ms.owl`); a vocabulary for which OLS names neither is an Error-3017 even with `--cvForce`.
. Library: `CvMappingValidator.of(CvMapping, MzTab, LookupPolicy, boolean)` validates one file with a `LookupPolicy` (source, strict or forced, `VocabularyCache`, `PreferredResources`, the current-release source), `CvMappingValidator.readMapping(URL)` reads a mapping, and `CvMappingValidator.resolvedVocabularies()` lists the releases used. For an offline run, pass `CurrentReleaseSource.offline("OLS")` as the current-release source, which names no release and is never asked. The existing factories and `CvParameterLookupService` constructors still use OLS, without version checks. New dependency of `jmztabm-validation`: `com.networknt:json-schema-validator`.
. Native validator: semantic validation (`-s`) ended with an `ExceptionInInitializerError` in the native binary: JXPath 1.4 reads `$java.home/lib/jxpath.properties`, and a native image has no `java.home`. The CLI now names JXPath's factory itself. The native metadata was traced again over the local lookup (OLS's ontology model, json-schema-validator's messages and its Jackson probes, commons-logging), and the jar/native parity check now runs one semantic validation per example file of at most 512 KiB (larger ones are listed as skipped) with the local lookup, offline, on a cache pre-filled from the test vocabularies under every MS version that the example files declare. It fails if fewer than half of these runs resolve a vocabulary from the cache. A weekly CI job runs the tests that need the network (`./mvnw -B verify -Pnetwork`).
